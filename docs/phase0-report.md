## 3) التحقق من الاستعادة

تمت الاستعادة في **PGlite 0.5.13** (PostgreSQL 18.6 مبني إلى WebAssembly) داخل المتصفح، لأن PostgreSQL المحلي في بيئة العمل كان يتعطل عند تشغيل العمليات الخلفية (`0xC0000142`)، والخادم المحلي محظور (`SocketException`).

### خطوات الاستعادة

1. إنشاء أدوار `anon` و`authenticated` و`service_role` و`supabase_admin`.
2. إنشاء `auth.users` (35 عموداً) و`auth.identities` (9 أعمدة) و`auth.uid()`.
3. تحميل `public_schema.sql` بعد استبدال `CREATE SCHEMA public;`.
4. تحميل `auth_data.sql` ثم `public_data.sql`.
5. إنشاء مشغّلي `on_auth_user_created` و`protect_demo_account` على `auth.users` **بعد** تحميل البيانات (لتفادي تكرار الملفات الشخصية).
6. إعادة `row_security = on` بعد أن كان pg_dump قد أوقفه.

### اختبارات RLS قبل التحصين وبعده

نجحت **25/25** اختباراً:

- الحساب التجريبي يرى 7 ملاحظات وملفه الشخصي فقط.
- المستخدم الثاني يرى ملاحظة واحدة فقط.
- لا قراءة ولا تعديل ولا حذف لملاحظات مستخدم آخر.
- لا إدراج ملاحظة باسم مستخدم آخر.
- `anon` مرفوض على الجداول والدوال.
- الحساب التجريبي لا يُحذف، وكلمة مروره لا تُغيَّر.
- حذف الحساب العادي يعمل ويحذف الملف الشخصي والملاحظات، وتم التحقق منه داخل معاملة مع تراجع.
- الكائنات الجديدة التي ينشئها `postgres` أصبحت deny-by-default.
- إنشاء مستخدم Auth جديد ما زال ينشئ ملفاً شخصياً تلقائياً.

الأعداد النهائية بعد الاختبارات: **2 profiles، 8 notes، 2 auth users، 2 identities** — دون أي تغيير في البيانات.

## 4) التحصين المطبَّق

الملف:

```text
supabase/migrations/001_harden_privileges.sql
```

### قبل التحصين

- `anon` يستطيع تنفيذ الدوال الأربع، بما فيها دوال المشغّلات.
- `authenticated` يملك `DELETE` مباشر على `profiles`.
- `authenticated` يستطيع تنفيذ دوال المشغّلات مباشرة.
- الامتيازات الافتراضية لـ`postgres` تمنح `anon`/`authenticated` صلاحيات كاملة على الكائنات الجديدة، و`PUBLIC` يملك `EXECUTE` افتراضياً على الدوال.

### بعد التحصين

| الكائن | `anon` | `authenticated` | `service_role` |
| --- | --- | --- | --- |
| `public.notes` | لا شيء | `SELECT, INSERT, UPDATE, DELETE` | كل الصلاحيات |
| `public.profiles` | لا شيء | `SELECT, INSERT, UPDATE` فقط | كل الصلاحيات |
| `delete_own_account()` | لا تنفيذ | تنفيذ | تنفيذ |
| `handle_new_user()` | لا تنفيذ | لا تنفيذ | تنفيذ |
| `protect_demo_account()` | لا تنفيذ | لا تنفيذ | تنفيذ |
| `set_updated_at()` | لا تنفيذ | لا تنفيذ | تنفيذ |

- `USAGE` على مخطط `public` فقط، دون `CREATE`.
- الامتيازات الافتراضية لـ`postgres` في `public`: الجداول والتسلسلات والدوال لـ`postgres` و`service_role` فقط.
- الامتياز الافتراضي العام لدوال `postgres`: `{postgres=X/postgres}` — لا `PUBLIC`.
- دوال `SECURITY DEFINER` تحتفظ بـ`search_path = ''`.

### تحقق الإنتاج

تم تشغيل الـMigration عبر `psql` داخل معاملة واحدة مع `ON_ERROR_STOP=1`، ونجحت كل التحققات الداخلية. ثم تم التحقق من:

- مصفوفة الصلاحيات أعلاه مطابقة.
- عزل RLS: 7/1 و1/0.
- رفض `anon` وحذف `profiles` وتنفيذ دوال المشغّلات.
- رفض حذف الحساب التجريبي وتغيير كلمة مروره.
- CRUD كامل للملاحظات وتحديث الملف الشخصي داخل معاملات مع تراجع.
- إنشاء كائنات جديدة deny-by-default.
- إنشاء مستخدم Auth جديد مع ملف شخصي تلقائي.
- بقاء الأعداد: 2/8/2/2.

## 5) المخاطر المتبقية

1. **امتيازات `supabase_admin` الافتراضية:** ما زالت تمنح `anon`/`authenticated` صلاحيات كاملة على الكائنات التي ينشئها هذا الدور في `public`. لا يملك `postgres` صلاحية تعديلها (ليس عضواً في `supabase_admin` وليس superuser).  
   **التخفيف:** إنشاء الكائنات عبر migrations تُنفَّذ بدور `postgres`، وتفعيل RLS صراحةً، أو تطبيق نفس `ALTER DEFAULT PRIVILEGES` عبر اتصال يملك `supabase_admin`.

2. **تدوير المفتاح السري `sb_secret_...`:** لم يُنفَّذ بعد. الملف المحلي لا يحتوي رمز وصول إداري (personal access token)، ولا يمكن تدوير المفتاح من قاعدة البيانات.  
   **الإجراء:** من لوحة Supabase → Project Settings → API Keys → Secret keys، أنشئ مفتاحاً جديداً، احذف القديم، ولا تضعه في أي محادثة أو مستودع. التطبيق الثابت لا يستخدم المفتاح السري؛ يستخدم Publishable key فقط.

3. **SMTP والتسجيل:** التسجيل العام معطّل (`disable_signup=true`) وتأكيد البريد مفعّل (`mailer_autoconfirm=false`) حتى إعداد SMTP موثوق. هذا قرار مقصود وليس عطلاً.

4. **SQL Editor في Supabase:** ما زال يفشل أحياناً بـ`28P01` بعد تغيير كلمة مرور قاعدة البيانات. الحل الحالي هو `psql` المباشر. لا يؤثر على التطبيق.

5. **بيئة العمل المحلية:** PostgreSQL المحلي يتعطل عند تشغيل العمليات الخلفية، والخادم المحلي محظور. تم تجاوز ذلك بـPGlite، وهو أثر بيئي لا يخص الإنتاج.

## 6) خطة التراجع

- لا يوجد حذف جداول أو أعمدة أو بيانات في هذا التغيير.
- للتراجع عن الصلاحيات فقط: إعادة منح الصلاحيات السابقة يدوياً من `public_schema.sql` (غير مستحسن).
- للتراجع الكامل عن أي تغيير لاحق: استعادة `full.dump` في مشروع staging أولاً، ثم الإنتاج بعد التحقق.
